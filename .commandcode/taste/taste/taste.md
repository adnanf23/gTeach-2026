# Taste
- Maintains an `ARCHITECTURES.md` file at the repo root that defines the project's intended architecture, and expects the agent to read it and conform code to it — especially before large structural changes. Confidence: 0.9
- Prefers a strict one-way layered architecture: `components/ → actions/ → services/ → repositories/ → PocketBase`. `actions/` are thin `"use server"` delegates that only call services; business/aggregation logic belongs in `services/`; ALL PocketBase access (queries/CRUD) is confined to `repositories/`. Confidence: 0.85
- Prefers keeping existing behavior identical when refactoring structure — same function export names, same results/UI, only the location/layering changes. Confidence: 0.8
- Prefers applying the same pattern/change consistently across the whole app rather than incrementally or only to newly written code — including feature edits asked to land in parallel on equivalent pages of different roles (e.g. the same agenda time-slot options on both the guru-mapel and walikelas agenda pages). Confidence: 0.85
- Expects role-equivalent pages to reach full feature parity rather than a reduced subset — e.g. the admin and ICT rapor-print pages must support every rapor variant the walikelas rapor preview has (akademik/ASAS, tahfiz, kombinasi), not just the one that came up; he will correct an implementation that only covers part of the set (e.g. chasing that only AHB appears in the print pages while ASAS/Tahfizh are missing). Confidence: 0.7
- Communicates in Bahasa Indonesia — writes instructions and questions in Indonesian and expects responses in the same language. Confidence: 0.9
- Does not want changes pushed to git until explicitly told to; keeps work local/unpushed during a refactor (works on a dedicated refactor branch). Confidence: 0.85
- When a cross-cutting change spans many pages, prefers delivering it role-by-role / folder-by-folder with a build verification between batches, rather than one all-at-once pass. Confidence: 0.75
- When optimizing performance, prefers concrete mechanical techniques: eliminate double/duplicate data loads, parallelize independent queries with `Promise.all`, add server-side `filter` and `fields` projection to cut over-fetching, and move heavy aggregation off the client to the server. Confidence: 0.7
- Prefers solutions that avoid touching the PocketBase schema: reuse fields that already exist (e.g. filter `nilai_*` by `tahun_ajaran_id`, derive period bounds from `tahun_ajaran.Mulai/Akhir`) instead of adding new fields; explicitly says the schema is just the schema and must not be edited ("itu hanya skema ga usah di edit"). Confidence: 0.75

Confidence: 0.6
