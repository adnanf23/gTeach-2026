# Taste
- Maintains an `ARCHITECTURES.md` file at the repo root that defines the project's intended architecture, and expects the agent to read it and conform code to it — especially before large structural changes. Confidence: 0.9
- Prefers a strict one-way layered architecture: `components/ → actions/ → services/ → repositories/ → PocketBase`. `actions/` are thin `"use server"` delegates that only call services; business/aggregation logic belongs in `services/`; ALL PocketBase access (queries/CRUD) is confined to `repositories/`. Confidence: 0.85
- Prefers keeping existing behavior identical when refactoring structure — same function export names, same results/UI, only the location/layering changes. Confidence: 0.8
- Prefers applying the same pattern/change consistently across the whole app rather than incrementally or only to newly written code — including feature edits asked to land in parallel on equivalent pages of different roles (e.g. the same agenda time-slot options on both the guru-mapel and walikelas agenda pages). Confidence: 0.8
- Communicates in Bahasa Indonesia — writes instructions and questions in Indonesian and expects responses in the same language. Confidence: 0.9
- Does not want changes pushed to git until explicitly told to; keeps work local/unpushed during a refactor (works on a dedicated refactor branch). Confidence: 0.85
- When a cross-cutting change spans many pages, prefers delivering it role-by-role / folder-by-folder with a build verification between batches, rather than one all-at-once pass. Confidence: 0.75
- When optimizing performance, prefers concrete mechanical techniques: eliminate double/duplicate data loads, parallelize independent queries with `Promise.all`, add server-side `filter` and `fields` projection to cut over-fetching, and move heavy aggregation off the client to the server. Confidence: 0.7
- Prefers solutions that avoid touching the PocketBase schema: reuse fields that already exist (e.g. filter `nilai_*` by `tahun_ajaran_id`, derive period bounds from `tahun_ajaran.Mulai/Akhir`) instead of adding new fields. Confidence: 0.55
- Prefers user-facing, selectable filters (e.g. a semester dropdown listing all periods, defaulting to the active one) over silently restricting data to just the current period. Confidence: 0.5
- Expects precise, non-overstated scope claims — asks whether work is really "all" done and wants an honest accounting of what remains (e.g. deliberate exceptions left on the client). Confidence: 0.55
- Decides the exact scope of a feature himself and will correct an over-broad application — do not spread a change wider than asked. Example: wanted the semester filter only on agenda (agenda mengajar) and penilaian pages, keeping all absensi pages purely time-range based (no semester filter/sort). Confidence: 0.6
- Verifies behavior manually in the browser (pages require login) and expects to be enabled/told how to self-validate — e.g. asks "how do I validate?", inspects the Network tab and reads dev-server action logs to confirm results. Confidence: 0.5
- Wants user-facing success/failure feedback for operations — explicitly asks that a feature end with a "berhasil atau gagal" (success or failure) notification. Confidence: 0.5
- Specs features as detailed, ordered, multi-step lists (e.g. a numbered 1–9 workflow), expecting each step implemented as described. Confidence: 0.5
- Expects new pages to be styled "modern" and visually consistent with the rest of the app ("sama seperti halaman lainnya") — reuse the existing design language (slate/indigo palette, cards, badges, lucide-react icons) rather than a plain utilitarian layout. Confidence: 0.7
- Communicates UI/design requirements by supplying a reference screenshot/mockup and saying "buat seperti ini", expecting the implementation to closely replicate the reference layout (structure, spacing, stepper/columns, component styling) rather than just approximate it. Confidence: 0.6
- For generated Excel/data exports, expects the output to be "rapi": rows sorted naturally by class level (1→6, then class name, then student name) instead of arbitrary order, plus polished columns — human-readable header labels, frozen header row, thin cell borders, auto-fit widths, and numeric columns centered. Confidence: 0.5
- Prefers Excel exports split into one worksheet per logical grouping — one sheet per semester (absensi), one sheet per class (nilai), separate sheets per role group (walikelas, guru mapel) — instead of cramming everything into a single sheet. Confidence: 0.7
- For any import flow, expects a downloadable template (correct headers, one example row, dropdown validation for enumerated fields like role/jenis_kelamin) made available in the import UI before the user uploads anything. Confidence: 0.65
- Expects a "backup database" action to actually download the backup file to the user's machine (a real download), not merely create it server-side or open a URL in a new tab. Confidence: 0.55
